## Зачем нужно

Частый вопрос по Postgres: когда JSONB уместен vs нормализованные колонки, как искать и индексировать, чем отличается от JSON.

## Как работает

`JSON` хранит текст как есть; **JSONB** парсит в бинарную структуру (порядок ключей не сохраняется, дубликаты схлопываются). Операторы: `->` / `->>`, `@>`, `?`. Индекс **GIN** ускоряет containment/`@>`.

Паттерн: стабильные поля — обычные колонки + constraints; редкие/эволюционирующие атрибуты — JSONB. Можно комбинировать generated columns / expression indexes по пути.

Docs: [JSON Types](https://www.postgresql.org/docs/current/datatype-json.html).

## Что спрашивают

- JSON vs JSONB в PostgreSQL?
- Когда JSONB — плохая идея?
- Как индексировать поиск по ключу/пути?

## Ответы

### JSON vs JSONB в PostgreSQL?

**JSON** — точный текстовый снимок (сохраняет пробелы/порядок). **JSONB** — разобранное хранение, лучше для запросов и индексов. В приложениях почти всегда берут JSONB.

### Когда JSONB — плохая идея?

Когда поля стабильны, по ним фильтруют/джойнят и нужны constraints/FK/статистика планировщика как у колонок. JSONB без дисциплины раздувает строки, усложняет миграции и проверки («обязательный ключ внутри JSON» без CHECK/generated — хрупко).

### Как индексировать поиск по ключу/пути?

GIN по всей JSONB для `@>` / existence; expression/ partial index на `(data->>'status')` или generated column, если фильтр узкий и частый. Сначала смотрите EXPLAIN — «просто GIN на всё» не всегда выигрывает.
