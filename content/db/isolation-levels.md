## Зачем нужно

Без понимания изоляции код «прочитал — проверил — записал» легко нарушает бизнес-инвариант при параллельных запросах, хотя каждая транзакция отдельно успешна.

## Как работает

SQL определяет Read Uncommitted, Read Committed, Repeatable Read и Serializable через запрещённые аномалии. Реализация зависит от СУБД: PostgreSQL использует MVCC, а его Read Uncommitted равен Read Committed. Serializable должен давать эффект некоторого последовательного порядка, но может завершать транзакцию serialization failure.

## Практические нюансы

Уровень не заменяет ограничения и блокировки. Для списания денег полезны `CHECK`/уникальность, атомарный `UPDATE ... WHERE`, иногда `SELECT ... FOR UPDATE`. Транзакции на Serializable нужно уметь повторять целиком с backoff; изменение уровня не следует использовать как случайный фикс.

## Что спрашивают

- Какие аномалии предотвращают уровни изоляции?
- Чем Repeatable Read отличается от Serializable?
- Как выбрать уровень изоляции для операции?

## Ответы

### Какие аномалии предотвращают уровни изоляции?

Dirty read — чтение незакоммиченного; non-repeatable read — повторное чтение строки даёт другое значение; phantom — меняется набор строк предиката; write skew — две транзакции читают общий инвариант и меняют разные строки. Точные гарантии надо сверять с документацией конкретной СУБД.

### Чем Repeatable Read отличается от Serializable?

Repeatable Read обычно фиксирует snapshot и защищает повторные чтения, но не обязан предотвращать все аномалии сериализации, например write skew. Serializable гарантирует эквивалент последовательного выполнения ценой ожиданий, abort и retry.

### Как выбрать уровень изоляции для операции?

Сначала формулируют инвариант и конкурентный сценарий, затем выбирают минимальную гарантию и дополняют её constraint, условным update или lock. Решение проверяют параллельным тестом, а не только happy path.
