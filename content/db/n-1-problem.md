---
title: Проблема N+1 запросов
summary: N+1 возникает, когда приложение делает один запрос за списком и затем по запросу на каждый элемент. Latency и нагрузка растут с размером результата.
---

## Зачем нужно

Проблема особенно скрытна в ORM и GraphQL: код выглядит локально, а сетевые round trips появляются лениво.

## Как работает

После `SELECT posts` обращение к `post.author` может выполнить N отдельных `SELECT users WHERE id=?`. Исправляют eager loading/join, batch-запросом `WHERE id IN (...)`, DataLoader или заранее спроектированной projection. Цель — ограниченное число запросов на операцию.

## Практические нюансы

Один огромный JOIN не всегда лучше: связи one-to-many размножают строки и данные. Нужны pagination, batching и измерение bytes/rows. N+1 находят по tracing, query count в тестах и повторяющимся SQL, а не только по CPU базы.

## Что спрашивают

- Как распознать N+1?
- Как исправить N+1 в ORM?
- Почему JOIN может ухудшить ситуацию?

## Ответы

### Как распознать N+1?

Число SQL-запросов линейно растёт с количеством объектов; в trace видна серия почти одинаковых запросов с разными id. Полезен integration test с верхней границей query count.

### Как исправить N+1 в ORM?

Явно загрузить нужную связь (`include`/`join fetch`) или собрать ids и сделать batch query. Выбор зависит от cardinality и pagination; отключение lazy loading помогает сделать стоимость явной.

### Почему JOIN может ухудшить ситуацию?

При нескольких one-to-many связях получается декартово размножение, растут передаваемые данные и память ORM. Иногда два-три batched query эффективнее одного широкого join.
