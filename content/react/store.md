title: Глобальный store
summary: Store централизует разделяемое client state и задаёт предсказуемый протокол чтения, обновления и подписки компонентов.
---

## Зачем нужно

Store оправдан, когда состояние используют далёкие части дерева, обновления сложны или нужны devtools и воспроизводимость. Он не заменяет локальный state и кеш server state.

## Как работает

Store хранит snapshot. Компоненты подписываются на выбранный selector, а actions создают следующий snapshot напрямую или через reducer. Хорошая интеграция с React предоставляет согласованные snapshots при concurrent rendering, например через `useSyncExternalStore`.

Гранулярный selector уменьшает ререндеры; возвращающий новый объект selector может требовать shallow equality или мемоизации. Состояние делят по доменным границам, но не дублируют вычисляемые данные. Middleware может добавить persistence, логирование и async orchestration, ценой неявности.

## Что спрашивают

- Когда нужен store, а когда достаточно Context?
- Что хранить в глобальном store не следует?
- Как selector влияет на ререндеры?

## Ответы

### Когда нужен store, а когда достаточно Context?

Context удобен для редко меняющихся зависимостей и значений одного поддерева. Store полезен при частых независимых обновлениях, селекторах, действиях, middleware и инструментах отладки. Размер приложения сам по себе не критерий.

### Что хранить в глобальном store не следует?

Локальное состояние одного виджета, производные значения и удалённый кеш, если им уже управляет query-библиотека. Глобализация увеличивает время жизни данных и связанность.

### Как selector влияет на ререндеры?

Подписчик должен обновляться, когда выбранное значение изменилось по принятому сравнению. Узкий selector изолирует изменения; новый объект на каждый вызов делает результат нестабильным и вызывает лишние рендеры.
