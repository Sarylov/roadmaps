## Зачем нужно

Самый частый источник багов на фронт-собесе и в проде: бесконечные запросы, устаревшие closures, забытый cleanup. Нужно чётко отличать «эффект» от рендера.

## Как работает

```js
useEffect(() => {
  const id = setInterval(tick, 1000)
  return () => clearInterval(id) // cleanup
}, [tick])
```

После отрисовки React вызывает эффект. При смене deps — cleanup предыдущего, потом новый. `[]` — mount/unmount (с оговорками Strict Mode). Не для вычислений во время render — для этого обычные переменные / `useMemo`.

Docs: [Using the Effect Hook](https://react.dev/reference/react/useEffect).

## Что спрашивают

- Когда нельзя класть логику в `useEffect`?
- Зачем cleanup и что будет без него?
- Почему объект/массив в deps даёт лишние запуски?

## Ответы

### Когда нельзя класть логику в `useEffect`?

Если можно вычислить во время render (derived state) — **не** эффект. Трансформации props→UI, фильтрация списка — в теле компонента. Эффект — когда трогаете **внешний мир**: сеть, DOM-подписки, `localStorage` sync, таймеры. Также не заменяйте им поток данных «state A → setState B» без нужды — часто лишний render и гонки.

### Зачем cleanup и что будет без него?

Cleanup снимает подписку/таймер/abort контроллер **перед** новым эффектом и при unmount. Без него — утечки, двойные listeners, setState на размонтированном дереве, продолжающийся fetch. В Strict Mode React намеренно mount→cleanup→mount, чтобы это ловить.

### Почему объект/массив в deps даёт лишние запуски?

Сравнение deps — **Object.is**. Новый литерал `{}` / `[]` / inline-функция на каждый render → deps «изменились» → эффект каждый раз. Стабилизируйте: `useMemo`/`useCallback`, примитивы, или пересмотрите, нужен ли объект в deps.
