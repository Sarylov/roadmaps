---
title: React.memo
summary: `React.memo` пропускает ререндер компонента, если его props не изменились по поверхностному сравнению; это точечная оптимизация, а не гарантия.
---

## Зачем нужно

`memo` полезен для дорогих часто рендерящихся поддеревьев, но бессистемная мемоизация усложняет код и нередко ничего не ускоряет.

## Как работает

При ререндере родителя React обычно вызывает детей. Компонент в `memo` может сделать bailout, если каждый prop равен предыдущему по `Object.is`. Новые объекты, массивы и функции ломают это условие; иногда ссылки стабилизируют через `useMemo` и `useCallback`, но только при измеримой пользе.

Собственное state, изменившийся context или внутреннее обновление всё равно рендерят компонент. Пользовательский comparator допустим, но обязан корректно сравнить каждый prop, включая функции; глубокое сравнение может оказаться дороже рендера и вернуть устаревшее замыкание.

## Что спрашивают

- Когда `React.memo` действительно полезен?
- Почему `memo` не помогает при новом объекте в props?
- Может ли мемоизированный компонент всё равно ререндериться?

## Ответы

### Когда `React.memo` действительно полезен?

Когда Profiler показывает дорогой повторный рендер, компонент часто получает одинаковые props, а его пропсы можно сохранять стабильными. Для дешёвого компонента стоимость сравнения и сложность могут превысить выигрыш.

### Почему `memo` не помогает при новом объекте в props?

Поверхностное сравнение проверяет ссылку: `{}` на каждом рендере не равен предыдущему `{}`. Лучше передать примитивы, поднять константу или мемоизировать вычисление при корректных зависимостях.

### Может ли мемоизированный компонент всё равно ререндериться?

Да. `memo` касается props от родителя. Изменение собственного state, читаемого context или решение React повторить render не блокируется; поэтому `memo` считается оптимизационной подсказкой.
