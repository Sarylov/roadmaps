summary: Локальное состояние принадлежит конкретной позиции компонента в React-дереве и подходит для UI-данных с узкой областью использования.
---

## Зачем нужно

Правильное размещение state уменьшает связанность и число ререндеров. Преждевременный глобальный store превращает временное состояние формы или меню в общий протокол приложения.

## Как работает

`useState` хранит значение между рендерами Fiber. Обновление ставится в очередь и планирует рендер; значение текущего рендера остаётся snapshot, поэтому несколько зависимых обновлений делают функциональной формой `setCount(c => c + 1)`.

State следует держать у ближайшего общего владельца компонентов, которым он нужен. Его поднимают вверх только для синхронизации. Производные значения обычно вычисляют во время render, а не дублируют в state. Объекты и массивы обновляют иммутабельно, чтобы сохранить старый snapshot и дать React заметить новую ссылку.

## Что спрашивают

- Где размещать состояние, используемое двумя компонентами?
- Почему state нельзя изменить обычным присваиванием?
- Когда не нужно хранить значение в state?

## Ответы

### Где размещать состояние, используемое двумя компонентами?

У их ближайшего общего предка либо в специализированном внешнем источнике, если владельцем является не UI. Не стоит автоматически поднимать state до корня приложения.

### Почему state нельзя изменить обычным присваиванием?

Присваивание не ставит обновление в очередь и мутирует snapshot, на который может опираться текущий render. Setter сообщает React о новой версии данных и позволяет планировать обновление.

### Когда не нужно хранить значение в state?

Если оно полностью выводится из props и другого state, вычисляется дёшево или не влияет на отображение. Производный state создаёт две версии истины и риск рассинхронизации; служебную mutable-ссылку можно хранить в `ref`.
