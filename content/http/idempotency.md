title: HTTP idempotency
summary: Идемпотентная операция после повторов имеет тот же наблюдаемый эффект, что после одного вызова. Она критична, потому что timeout не сообщает клиенту, был ли request применён.
---

## Зачем нужно

Тема регулярно встречается на backend-интервью: сильный ответ связывает механизм с наблюдаемым поведением, отказами и production-решением.

## Как работает

GET/PUT/DELETE семантически идемпотентны, но бизнес-реализация обязана это сохранить. Для POST клиент может прислать idempotency key; сервер атомарно сохраняет key, fingerprint запроса и итоговый response в области tenant.

- Какие trade-offs важно назвать для HTTP idempotency?

## Ответы

### Как работает HTTP idempotency на практике?

GET/PUT/DELETE семантически идемпотентны, но бизнес-реализация обязана это сохранить. Для POST клиент может прислать idempotency key; сервер атомарно сохраняет key, fingerprint запроса и итоговый response в области tenant.

### Какой типичный failure mode связан с HTTP idempotency?

Проверка «есть ли key» затем выполнение без unique constraint имеет race. Повтор с тем же key и другим body нельзя молча принять; TTL короче окна retry снова допускает дубль.

### Какие trade-offs важно назвать для HTTP idempotency?

Дедупликация требует atomic insert/transaction и возврата прежнего результата. Побочные эффекты после commit доставляют через outbox; exactly-once сеть не даёт, поэтому consumer тоже проектируют идемпотентным.
