## Зачем нужно

Без правильных статусов фронт не отличит «нет данных» от «нет прав», а бэкенд ломает кэш, ретраи и мониторинг.

## Базовые классы

- **2xx** — успех (`200 OK`, `201 Created`, `204 No Content`)
- **3xx** — редирект (`301`, `302`, `304 Not Modified`)
- **4xx** — ошибка клиента (`400`, `401`, `403`, `404`, `409`, `429`)
- **5xx** — ошибка сервера (`500`, `502`, `503`)

Справочник: [MDN — HTTP response status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status).

## Что спрашивают

- `401` vs `403`?
- Когда `204`, а когда `200` с пустым телом?
- Идемпотентность методов и какие статусы типичны для `PUT`/`DELETE`?

## Ответы

### `401` vs `403`?

**401 Unauthorized** — «кто ты?» нет / неверная аутентификация (часто с `WWW-Authenticate`). Клиент может повторить с credentials.

**403 Forbidden** — «знаю кто ты, но нельзя». Права/политика не пускают; просто «подставить другой пароль» обычно не поможет.

### Когда `204`, а когда `200` с пустым телом?

**204 No Content** — успех, **тела нет** (и не должно быть). Удобно для `DELETE` / `PUT`, когда клиенту нечего парсить.

**200** с пустым телом формально допустим, но хуже семантики: клиент ждёт entity. Для «успех без полезной нагрузки» предпочтительнее 204; для «вот ресурс/результат» — 200 + тело (`201` при создании).

### Идемпотентность методов и какие статусы типичны для `PUT`/`DELETE`?

Идемпотентный метод: N одинаковых запросов → тот же эффект, что один. `GET`, `PUT`, `DELETE` — идемпотентны по спецификации; `POST` — нет.

Типично: `PUT` → `200`/`204` (обновили) или `201` (создали); `DELETE` → `200`/`204` или `404`, если уже нет (оба варианта обсуждаемы; важно быть консистентным). Повтор `DELETE` не должен снова «ломать» мир.
