## Зачем нужно

В микросервисах и платежах ретраи неизбежны. Без идемпотентности получите двойное списание, два заказа, два события.

## Как работает

1. Клиент шлёт `Idempotency-Key: <uuid>`.
2. Сервер сохраняет ключ + результат первой обработки.
3. Повтор с тем же ключом возвращает тот же результат, не выполняя побочный эффект снова.

Связано с transactional outbox, dedup keys в consumer’ах Kafka/RabbitMQ.

Эталон: [Stripe — Idempotent requests](https://docs.stripe.com/api/idempotent_requests).

## Что спрашивают

- Чем идемпотентность метода HTTP отличается от idempotency key?
- Где хранить ключи и какой TTL?
- Как связать outbox и идемпотентный consumer?

## Ответы

### Чем идемпотентность метода HTTP отличается от idempotency key?

Идемпотентность **метода** (`PUT`/`DELETE`) — свойство семантики HTTP: повтор того же запроса безопасен по смыслу протокола.

**Idempotency-Key** — прикладной механизм для **неидемпотентных** операций (`POST` платежа): клиент даёт ключ, сервер гарантирует один побочный эффект на ключ, даже если сеть ретраит. Метод может быть POST, а операция — идемпотентной благодаря ключу.

### Где хранить ключи и какой TTL?

Обычно Redis / DB таблица: `key → status + response` (или hash запроса). TTL — горизонт ретраев клиента (минуты–сутки; у Stripe — порядка 24h). Нужны атомарность «проверил ключ / зарезервировал / записал результат» и одинаковый ответ на повтор (или 409 при конфликте тела).

### Как связать outbox и идемпотентный consumer?

**Outbox**: в одной транзакции с бизнес-записью пишем событие; паблишер шлёт в брокер — at-least-once на публикации.

**Consumer**: обрабатывает at-least-once → нужен **dedup / idempotency** по `eventId` (или business key): «уже обработал — skip». Вместе: ровно одна бизнес-фиксация на стороне писателя + ровно одна обработка на стороне читателя при ретраях.
