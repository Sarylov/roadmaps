---
title: SQL Injection
summary: SQL injection возникает, когда ввод пользователя меняет структуру SQL-команды. Основная защита — параметризованные запросы и строгие границы для динамических идентификаторов.
---

## Зачем нужно

Уязвимость позволяет читать или менять чужие данные, обходить авторизацию и иногда выполнять административные операции от имени DB user.

## Как работает

Конкатенация `"... WHERE email='" + input + "'"` смешивает код и данные. Prepared statement отправляет SQL-шаблон и значения раздельно, поэтому значение не становится оператором. ORM безопасен только пока используются его параметры, а не raw string interpolation.

## Практические нюансы

Параметры обычно нельзя использовать для имени таблицы, колонки или направления сортировки — здесь нужен allowlist. Least-privilege DB role ограничивает ущерб, но не заменяет параметры. Тестируют позитивные и негативные случаи, а секретные SQL/значения не пишут в логи.

## Что спрашивают

- Почему escaping хуже параметризованного запроса?
- Как безопасно сделать динамический ORDER BY?
- Защищает ли ORM от SQL injection?

## Ответы

### Почему escaping хуже параметризованного запроса?

Escaping зависит от диалекта, кодировки и контекста и легко забывается. Параметризация на уровне драйвера принципиально отделяет синтаксис от значения.

### Как безопасно сделать динамический ORDER BY?

Сопоставить внешний enum с заранее заданными SQL-фрагментами, например `createdAt -> created_at`; неизвестные значения отклонять. Передавать имя колонки как value parameter нельзя.

### Защищает ли ORM от SQL injection?

Query builder обычно параметризует values, но raw SQL, template interpolation и динамические identifiers остаются опасными. Проверять нужно итоговый API и bindings.
